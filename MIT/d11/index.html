What is System Design?

  • Definition: The process of defining the architecture, components, modules, interfaces, and data for a system to satisfy specified requirements.
  • Why it matters: Bridges the gap between raw coding and building production-ready, scalable applications.
  • The Goal: Building systems that are reliable, scalable, and maintainable.

High-Level Design (HLD)

  • Scope: The "Bird's Eye View" of the entire system.
  • Focus: System architecture, databases, load balancers, caching layers, and inter-service communication.
  • Output: Block diagrams, flowcharts, and defining tech stacks.
  • Target Audience: Software Architects, Product Managers, and Stakeholders.

Low-Level Design (LLD)

  • Scope: The microscopic view of individual components.
  • Focus: Classes, interfaces, data structures, algorithms, and design patterns.
  • Output: Class diagrams, entity-relationship diagrams (ERD), and exact API signatures.
  • Target Audience: Developers and QA Engineers.

HLD vs LLD: Key Differences

  • Abstraction: HLD is highly abstract; LLD is highly detailed.
  • Creation Phase: HLD is created first (System Architecture); LLD is created next (Component Design).
  • Tools: HLD uses System Context diagrams; LLD uses UML (Unified Modeling Language).
  • Interview Context: HLD tests infrastructure knowledge; LLD tests Object-Oriented Programming (OOP) and SOLID principles.

Core Concepts: Scalability

  • Vertical Scaling (Scaling Up): Adding more power (CPU, RAM) to an existing machine. Limited by hardware maximums.
  • Horizontal Scaling (Scaling Out): Adding more machines to your pool of resources. Virtually infinite but adds complexity.
  • Industry Standard: Modern distributed systems heavily rely on horizontal scaling.

Load Balancing

  • Purpose: Distributes incoming network traffic across multiple servers to ensure no single server bears too much demand.
  • Algorithms: Round Robin, Least Connections, IP Hash.
  • Benefits: Increases reliability, availability, and capacity. Prevents single points of failure (SPOF).

Caching Strategies

  • What it is: Temporary storage layer that stores a subset of data for ultra-fast retrieval.
  • Tools: Redis, Memcached.
  • Strategies:
    • Cache Aside (Lazy Loading)
    • Write-Through
    • Write-Back
  • Eviction Policies: LRU (Least Recently Used), LFU, FIFO.

Database Scaling

  • Replication: Creating copies of the database (Master-Slave architecture). Master handles writes; Slaves handle reads.
  • Sharding: Partitioning a database into smaller, faster, more easily managed parts called data shards.
  • Partitioning: Splitting data horizontally (by rows) or vertically (by columns).

The CAP Theorem

  • In a distributed data store, you can only guarantee two out of three:
  • Consistency: Every read receives the most recent write or an error.
  • Availability: Every request receives a non-error response, without guaranteeing it contains the most recent write.
  • Partition Tolerance: The system continues to operate despite an arbitrary number of messages being dropped by the network.

Microservices vs Monolith

  • Monolith: Single unified unit. Easy to develop and deploy initially, but hard to scale and maintain as the codebase grows.
  • Microservices: Suite of independently deployable, modular services. Highly scalable and fault-tolerant, but introduces network complexity and operational overhead.

Message Queues & Async Processing

  • Problem: Synchronous tasks block the user experience (e.g., video rendering, email sending).
  • Solution: Message Queues temporarily store tasks until a worker process can execute them.
  • Tools: Apache Kafka, RabbitMQ, Amazon SQS.
  • Benefit: Decouples services, provides backpressure management, and ensures guaranteed delivery.

Content Delivery Networks (CDN)

  • What it is: A geographically distributed network of proxy servers and their data centers.
  • Purpose: Serve static content (HTML, CSS, JS, Images, Video) to users from a server geographically closest to them.
  • Benefits: Drastically reduces latency, decreases server load, and protects against DDoS attacks.

Advanced Concept: Rate Limiting

  • Purpose: Controls the rate of traffic sent or received by a network. Prevents abuse and cascading failures.
  • Algorithms:
    • Token Bucket
    • Leaking Bucket
    • Fixed Window Counter
    • Sliding Window Log

Advanced Concept: Consistent Hashing

  • The Problem: Standard hashing (`hash(key) % N`) breaks down when servers (N) are added or removed, requiring massive data reshuffling.
  • The Solution: Maps data and servers to a virtual ring. When a server is added/removed, only `k/N` keys need to be remapped.
  • Use Cases: Distributed caches, DynamoDB, Cassandra.

The Interview Framework (REHAD)

  • Requirements: Clarify functional and non-functional requirements (Ask questions!).
  • Estimation: Back-of-the-envelope math (Traffic, Storage, Bandwidth).
  • High-Level Design: Draw the core components and data flow.
  • API Design: Define the contract between client and server.
  • Deep Dive: Scale the system, identify bottlenecks, add caches/sharding.

Non-Functional Requirements (NFRs)

  • Often overlooked but critical in interviews.
  • Latency: How fast must the system respond?
  • Throughput: How many requests per second (RPS) must it handle?
  • Consistency vs. Availability: Which is prioritized based on the business use case?

Company-Wise: Meta (News Feed)

  • Core Challenge: Extreme read-heavy system, rapid feed generation.
  • Architecture: Push (Fanout-on-write) vs Pull (Fanout-on-read) models.
  • Solution: Hybrid approach. Pre-compute feeds for active users (Push), compute on-demand for inactive users or celebrities with millions of followers (Pull).

Company-Wise: Amazon (Checkout System)

  • Core Challenge: High consistency, zero data loss, distributed transactions.
  • Architecture: Idempotent APIs (prevent double charging), Distributed Locking.
  • Database: Relational databases (ACID properties) for financial transactions; NoSQL for shopping cart state.

Company-Wise: Netflix (Streaming)

  • Core Challenge: Massive bandwidth, global low latency, heavy storage.
  • Architecture: Open Connect (Netflix's custom global CDN).
  • Process: Videos are split into chunks, transcoded into different resolutions/formats, and distributed globally to edge servers.

Company-Wise: Uber (Ride-Hailing)

  • Core Challenge: Real-time geolocation tracking, fast matching algorithms.
  • Architecture: WebSockets for real-time driver location updates.
  • Geospatial DB: QuadTrees or Google S2 Geometry to partition the map and efficiently find nearest drivers.

Company-Wise: Google (Web Crawler)

  • Core Challenge: Scale (billions of pages), politeness (not DDoSing servers), handling duplicate content.
  • Architecture: Seed URLs -> URL Frontier (Queue) -> DNS Resolver -> HTML Fetcher -> Content Extractor -> Storage.
  • Key Algorithms: Bloom Filters (to track visited URLs and save memory).

Industry Readiness: The Resume

  • Impact over Duties: Use the X-Y-Z formula: "Accomplished [X] as measured by [Y], by doing [Z]."
  • Metrics Matter: "Reduced latency by 40%" instead of "Made API faster."
  • Portfolio: GitHub is your modern resume. Open-source contributions and end-to-end deployed projects stand out.

Behavioral Interviews: STAR Method

  • Companies look for cultural fit and conflict resolution skills.
  • Situation: Set the scene and give necessary context.
  • Task: Describe your specific responsibility.
  • Action: Explain exactly what steps *you* took.
  • Result: Share the outcomes, heavily utilizing data and metrics.

DSA vs System Design

  • Data Structures & Algorithms: Tests your localized logic, code optimization, and ability to translate thought into syntax.
  • System Design: Tests your macro-level thinking, experience with real-world infrastructure, and trade-off analysis.
  • The Balance: Junior roles focus 80% on DSA. Senior roles focus heavily on System Design and Architecture.

Navigating Ambiguity

  • Interviews are deliberately vague. "Design Twitter" is not a complete prompt.
  • Your first 5-10 minutes should strictly be scoping the problem.
  • Write down the exact features you are building, and explicitly state what you are *excluding* from the scope.

The Power of Mock Interviews

  • System Design is a conversational interview. You cannot practice it silently on a whiteboard.
  • Think Out Loud: The interviewer is evaluating your thought process, not just the final architecture diagram.
  • Use platforms like Pramp, Exponent, or peer groups to practice vocalizing trade-offs.

Red Flags in Interviews

  • Buzzword Dropping: Using terms like "Kafka" or "Microservices" without knowing how they work.
  • One-Size-Fits-All: Suggesting NoSQL for every problem just because it scales easily.
  • Ignoring the Interviewer: Not picking up on hints or rejecting constraints provided by the interviewer.
